## 2. 关键决定与取舍

1. **`path` 不写进种子，由导入器按父链计算**：避免人工书写出与 `parent_id` 不一致的路径；同时落实了 F0.1 后置的"`path = 父.path + id + '/'`"校验（种子侧）。
2. **幂等靠 `wc_meta.seed_version`**：版本未变则整体跳过，不产生任何写入（开发库文件哈希不变，已实测）。版本升高时按 id upsert。
3. **只更新 `origin='seed'` 的行**（`ON CONFLICT … WHERE origin='seed'`）：用户节点即使与种子 id 冲突也不被覆盖（设计 §14 Q13：种子按引用，用户节点全量）。
4. **`_stamp` 作为 `created_at/updated_at`**：使导入结果与时间无关，重复导入不改变库内容，开发库不因导入产生无谓二进制差异。
5. **不导入 `categories.json`、`seed/demo/`**：本功能范围仅 M0 的"最小种子"，分类属 M3、示例属 M4／M5。

### 4.2 需求偏移

- 许可：初稿 `_license` 写了"CC0-1.0"，但仓库尚无许可证，属于**擅自声明未确认的事实**（PRD §0-11、§22.3）。已改为"随本仓库，尚未选定许可证"，并列入下方后置项请用户决定。
- 节点名称均为公开地理名称，无个人数据（PRD §0-12）。
- 未使用任何第三方数据集；未引用其他项目内容（PRD §0-13）。
- 无 PRD §19 "明确不做"的内容。

### 4.3 最简化设计

- 无新依赖。`seed.mjs` 两个导出均被使用（`loadNodeSeed` 被 `importNodeSeed` 与测试使用）。
- 没有做：增量 diff 导入、种子删除同步（种子节点被移除时不删库内行）、多种子文件注册机制 —— 当前只有一份种子，无对应需求。
- F0.1 遗留跟踪项：`db.mjs` 的 `DEV_DB / MIGRATIONS_DIR` 导出——现在 `NODE_SEED` 也只在 `db.mjs` 内部使用，测试各自定位文件。**三项导出均无外部使用者，已改为非导出常量**（见下）。
