# F3.1 节点读取服务（getNode／listChildren／getAncestors）

- 里程碑：M3（P1 地理核心）的一部分，提前做的原因：**不依赖 wrangler** ／ 日期：2026-11-10 ／ 提交：**暂不提交**（用户指示）
- 对应需求：FR-N1、N2、N3、N5；设计 §4.2（`path`、`children` 三态）、§4.4、§6.1（分页、错误格式）、§6.2（`GET /nodes/{id}`、`/children`、`/ancestors`）、§6.3（错误码）；M3 验收"无子节点不显示展开""API 区分确无子节点与尚未加载""数据库无关注类字段"

## 1. 做了什么

| 文件 | 职责 |
|---|---|
| [`worker/errors.mjs`](../../worker/errors.mjs) | `AppError` 与设计 §6.3 登记的 13 个错误码；未登记码抛错 |
| [`worker/nodes.mjs`](../../worker/nodes.mjs) | `getNode`、`listChildren`（游标分页）、`getAncestors`。入参是 D1 形 `db`，**与运行时无关**，普通 Node 即可测 |
| [`tests/nodes.test.mjs`](../../tests/nodes.test.mjs) | 9 项测试 |

**范围刻意不含**：HTTP 路由、鉴权、`POST/PATCH/DELETE /nodes`（写入）。路由属 M1（需要 Workers 运行时，受 B5／B6 阻塞）；写入服务单独成下一个功能。

## 2. 关键决定与取舍

1. **`children` 三态的落点**：`none`（`child_count = 0`，确无子节点）／`not_loaded`（有子节点，带 `count`）。设计还有 `loaded`，用于响应已附带子节点列表的场景；本功能的响应都不内嵌子列表，故 `loaded` 不出现，**留给前端在拿到 `listChildren` 后自行标注**，服务端不虚构。（跟踪项 → 检查 4.1）
2. **`child_count` 用相关子查询实时计算**，不落库（设计 §4.2）。计划显示走 `wc_nodes_children` 覆盖索引。
3. **游标 = `"sort_order:id"`**，按第一个冒号切分（`id` 可含 `.`、`-`，设计不允许 `/`，未禁止冒号，故只切第一个）；对调用方不透明。排序键 `(sort_order, id)`，保证同 `sort_order` 的节点稳定分页。
4. **返回列显式白名单**，不返回 `path／origin／search_norm／时间戳`：`path` 是内部实现，`origin` 的用途是导出区分（设计 §14 Q13）。
5. **祖先**：把 `path` 拆分，一次 `IN` 查询，并在应用层按路径顺序重排（`IN` 不保证顺序）。
6. `limit` 默认 20、上限 100（设计 §6.1）；类型必须是整数，字符串 `"5"` 也拒绝——路由层负责把查询字符串转数字，服务层不做宽松转换。

## 4. 合规检查

### 4.1 需求遗漏

| 要求 | 状态 |
|---|---|
| FR-N1 无子节点不显示展开 | ✅ 服务端以 `children.state='none'` 表达 |
| FR-N2 区分 `children_count=0` 与 `children_not_loaded` | ✅ `none` vs `not_loaded`；设计三态中的 `loaded` 由前端在已加载后使用，**不在服务端实现，已说明** |
| FR-N3 无关注类字段 | ✅ 表、返回值均有测试 |
| FR-N5 不强加统一层数 | ✅ 查询不依赖 `kind`，两条深度不同路径均可导航（测试覆盖法国 0 层、未央区 5 个祖先） |
| `GET /nodes/{id}`、`/children?cursor`、`/ancestors` 的业务逻辑 | ✅ 逻辑；**HTTP 端点本身未做**（M1） |
| 错误码与格式 | ✅ 13 个码；响应 JSON 格式的序列化在路由层（M1） |
| `POST /nodes`、`PATCH`、`DELETE` | ❌ 本功能不含 → 下一个功能 F3.2 |
| 详情模板、底图、前端导航 | ❌ 不属本功能 → M3 后续 |
| `E_NODE_IN_USE`、`E_CONFLICT` 等写入相关码 | 已登记，使用在 F3.2 |

### 4.2 需求偏移

- 无新字段、无新表、无新依赖。未引入关注类机制（PRD §0-4）。
- 排序方式（`sort_order, id`）是设计未明确的补充，已写入第 2 节；属实现细节，不改变需求。
- 分页对 `limit` 的类型严格，是设计 §6.1 的"默认 20、上限 100"的落实，不是新增需求。

### 4.3 最简化设计

- 三个函数全部对应设计 §6.2 的三个读端点，无多余导出；`DEFAULT_LIMIT／MAX_LIMIT` 对应设计 §6.1 的“默认 20、上限 100”，仅在文件内部使用（校验轮发现原先误导出且记录写错，已改为非导出，见 [V1 校验记录](V1-compliance-audit.md)）。
- 不做：缓存、`ETag`、批量取多个节点、搜索、子树统计。
- `AppError` 的"未登记码抛错"是防止后续写错码的最小防护（约 3 行），保留。

### 4.4 检查中发现并处置

| # | 发现 | 处置 |
|---|---|---|
| 1 | 9 项测试一次全过。担心断言过松，于是单独打印了 4 条真实查询计划核对 | 计划符合预期（见第 3 节）；其中"需要临时排序"属已知、同级量级的开销，已写入记录 |
| 2 | 初稿想让服务端返回 `loaded` 状态 | 删除：服务端在不内嵌子列表的响应里无法诚实地知道客户端是否已加载，虚构会造成语义不清 |
| 3 | `limit="5"` 是否应宽松接受 | 否，路由层转换，服务层严格。避免同一语义出现两种输入形式 |
