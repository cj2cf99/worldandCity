## 1. 做了什么

| 文件 | 职责 |

## 2. 关键决定与取舍

1. **只能写 `origin='user'` 的节点**。`origin`、`path`、`realm`、`search_norm`、时间戳全部由服务端决定，客户端传入即 `E_VALIDATION`（防止伪造“种子”身份，也避免绕过 `path` 校验）。`realm` 继承父节点：用户不能在 geo 树下建 celestial 节点。
2. **用户节点必须有父节点**：根节点只来自种子，保证 `wc_nodes_path` 的单根假设。
3. **幂等**（设计 §6.1）：同 `id` 且内容一致 → 返回已有资源（`created:false`）；同 `id` 内容不同 → `E_CONFLICT`。
4. **`PATCH` 只允许** `name／name_local／detail／sort_order`；`parent_id／kind／code／realm／path／id／origin` 一律 `E_VALIDATION`（`details.reason='immutable'`）。这是“v1 不支持移动”的落实；`kind` 与 `code` 也不改，避免详情模板与外部编码映射失效，**这是设计未明说的收紧**（见 4.2）。
5. **名称规范化后为空（纯标点）拒绝**：否则该节点永远检索不到。是验证中发现的边界，补了测试。
6. **`kind` 暂用格式校验**（`^[a-z][a-z0-9_]{0,31}$`），**未按 `cfg:public.kinds` 值域校验**：该配置属 M1（KV）。已在 4.1 登记。
7. **`DELETE`** 仅检查子节点；位置绑定检查（`has_locations`）随 `wc_item_locations` 迁移（M4）加入。
8. 单条语句写入，不使用 `batch`：单行 `INSERT`，天然原子。

## 4. 合规检查

### 4.1 需求遗漏

| 要求 | 状态 |

| `POST /nodes`：新建用户节点 | ✅ 逻辑；HTTP 层 → M1 |

| `DELETE /nodes/{id}`：“仅无子节点、无位置绑定时允许” | ⚠️ 仅实现“无子节点”；“无位置绑定”**尚无表可查**，随 M4 迁移补入，并补测试（跟踪项） |
| `kind` 值域由 `cfg:public.kinds` 校验（§4.2） | ❌ 本功能只做格式校验；值域校验 → M1 配置就绪后补（跟踪项） |

| 非 `GET` 需 `Origin` 校验、鉴权（§6.1、§9） | → M1 |

| 天体节点（`realm='celestial'`）创建 | 继承父节点 realm 已支持；天体种子与模板 → M6 |

### 4.2 需求偏移
- `PATCH` 禁止修改 `kind` 与 `code`：设计只写了“改名与详情；不支持移动”，**这是我的收紧**，理由见 §2-4。若审核认为应允许改 `kind`，放开即可，不影响其他代码。
- 只能修改/删除 `origin='user'` 节点（种子只读）：与设计 §14 Q13“种子节点按引用，用户节点全量”一致，属必要推论。
- 无新字段、无新表、无新依赖；无关注类机制（PRD §0-4）；未触及 PRD §19 项。
- 未新增视觉债务（无前端）。

### 4.3 最简化设计
- 三个函数对应三个端点，无额外导出（`NAME_MAX／DETAIL_MAX_BYTES` 已改为非导出，见 4.4-3）。
- 不做：批量创建、节点移动、软删除、撤销、`kind` 注册表、乐观锁。
- `search-norm.mjs` 单独成文件仅 3 行，因为 M4 搜索与此处共用；若 M4 不复用则并回。

| # | 发现 | 处置 |
