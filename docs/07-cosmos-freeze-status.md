## 2. 表现不佳、已冻结的三个特殊星云
创生之柱（M16）、三叶星云（M20）、马头星云（B33）。经过三轮路线（贴图板 → 体积渲染 → 观测图 2.5D 分层），**最终表现仍不理想**，现状冻结：
- 当前实现为 [F3.16](dev-log/F3.16-photo-layered-nebulae.md)：以用户提供的观测图为主体，加载时在浏览器里自动拆层，相机限制在小角度。
- 已知问题：
  1. 创生之柱：暗尘层让柱子偏红偏深；亮星提取偏粗；韦伯档标签未对位。
  2. M20：只有主体图一份，红色发射区偏平，暗尘和气体的层间立体感弱；放大没有细节层。
  3. 马头：底图分辨率低（768 像素宽）、带示意方框（去除未生效）；放大细节层与底图对位只是估计。
  4. 三个场景的层间视差没有留下多角度对照；缺手工抠层素材、AI 补充层。
  5. 图像来源、署名与许可**未核实**，仓库是公开的；`referpic/` 与 `web/public/nebula/` 提交前需用户确认。
- 取代掉的方案（体积渲染 F3.15）代码已删除，记录保留在开发记录里作为教训：软件渲染下很慢，且形态难以控制。

## 3. 恢复开发前需要优化的“加载逻辑”与“表现”
加载逻辑（主要问题）：
- 预览里切换到特殊星云或黑洞场景后，**加载很慢**（隐藏窗格、软件渲染下几十秒才完成；真机未测）。已知原因：
  - 场景在进入时才构建，构建内容包括：观测图拆层（1～4 百万像素的 JS 循环）、AT2019qiz 的 1400 粒子×361 帧积分（主线程同步）、多处程序化贴图。
  - 每个场景都是整张大图一次性解码与上传 GPU，没有按距离或缩放分级加载。
- 建议方向（待用户确认后再做）：拆层与积分挪到 Worker 或离线预处理成静态图（构建时生成，运行时只加载小图）；贴图按尺寸分档并懒加载细节层；进入场景前先显示低清占位；对象缓存与离开场景时释放纹理。
表现：
- 三个特殊星云换用更高分辨率、无方框、署名明确的素材；手工抠前景尘埃；对位后的细节层。
- 黑洞场景：真机帧率、V404 喷流可见性、三种相机；AT2019qiz 的相机与多尺度规则（见 [F3.14](dev-log/F3.14-black-hole-devours-star.md)）。
- 其余未验证项见各 dev-log 的“后置事项”。
